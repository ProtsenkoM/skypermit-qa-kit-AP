# Repository Guidelines

## Призначення репозиторію

Це QA-kit для SkyPermit. Його основна мета — створення й підтримка ручних тест-кейсів, чеклістів і тест-планів на основі вимог із `../skypermit/docs/`. Автоматизовані тести та зміни коду застосунку не є типовими задачами цього репозиторію, якщо користувач не попросив про них окремо.

Під час аналізу звіряй модель даних, state machine, API-контракт, frontend scope, бізнес-правила та уточнення. Не вигадуй очікувану поведінку: суперечності або прогалини фіксуй як open questions із посиланням на файл і розділ джерела.

## Структура проєкту

Планована структура:

```text
.
├── README.md
├── AGENTS.md
├── test-cases/          # тест-плани, набори кейсів і чеклісти
│   ├── api/
│   ├── business-rules/
│   └── ui/
└── .agents/
    └── skills/          # локальні інструкції для повторюваних QA-задач
```

Групуй матеріали за функціональністю, а не за датою створення. Використовуй `kebab-case` для назв файлів, наприклад `flight-request-lifecycle.md`. Кожен тест-кейс має містити ID, джерело вимоги, передумови, кроки, тестові дані, очікуваний результат і пріоритет.

## Джерело вимог і режим read-only

Репозиторій застосунку знаходиться в `../skypermit` і є лише джерелом контексту. Дозволені тільки операції читання, наприклад `rg`, `find`, `sed`, `git log`, `git diff` і перегляд файлів. Насамперед використовуй `../skypermit/docs/01-data-model.md` — `08-uml-diagrams.md`; код і наявні тести можна читати для перевірки реалізації, але вони не замінюють задокументовані вимоги.

Категорично заборонено в `../skypermit`:

- створювати, редагувати, перейменовувати або видаляти файли;
- запускати formatter, linter, build, dev server чи тести, якщо вони можуть створити кеш, coverage або інші артефакти;
- виконувати `npm install`, міграції, seed-скрипти або змінювати базу даних;
- змінювати Git-стан: commit, checkout, stash, reset, clean або перемикання гілок;
- змінювати `.env`, секрети, залежності чи конфігурацію.

Усі створені QA-артефакти зберігай лише в цьому репозиторії.

## Перевірка змін

Перед завершенням перевір `git diff --check`, `git status --short` і вручну звір трасування кожного очікуваного результату до документації. У тест-планах обов’язково охоплюй позитивні, негативні, граничні сценарії, ролі й дозволи, переходи станів та порядок gate-перевірок.

## Коміти та pull requests

Пиши короткі imperative commit subjects, наприклад `add flight request test plan`. У PR вказуй scope, використані джерела вимог, покриті ризики, відкриті питання та перелік доданих або змінених QA-артефактів.
